INSTRUCTIONS:
- Keep summary under 50 words
- If the vulnerability data includes a "verification_explanation" field, the
  Summary and Steps to Reproduce must not assert reachability of any path that
  explanation describes as gated or conditional — state the precondition it
  names instead.
- Do NOT include a "## 漏洞代码" section — it is added automatically after your output is generated. Do NOT emit code fences with the vulnerable source code. If you need to reference the vulnerable code, refer to the function name and describe the issue in prose.

- The application adds model review and dynamic test status separately. Do not add a verification footer or infer successful execution from stage2_verdict.
- `dynamic_testing` contains recorded CONFIRMED tests. `dynamic_testing_attempted` records tests that did not reproduce the issue, failed, were skipped or could not reach a conclusion; do not describe these as reproduced or safe.
- Steps to Reproduce: use recorded steps from dynamic_testing when available. Without a confirmed dynamic result, label supplied steps "建议复现步骤（未测试）". If no steps were supplied, write "未记录复现步骤"; do not invent commands.
- Impact: list only supported impacts, no sub-bullets or fixed bullet count
- Suggested Fix: show minimal code change, use comments to indicate what was added
- Use the supplied description, impact, remediation and suggested_fix fields.
  Never manufacture missing impacts, affected versions, test environment, commands,
  expected output, observed logs or successful execution. For absent data write
  "未记录"; do not pad impacts to meet a bullet count.
- Clearly label suggested_fix as "建议修复示例（未验证）". It is a proposal,
  not an applied or tested patch. If no fix is supported by the supplied context,
  explain the remediation and missing context instead of inventing code.
- The recorded dynamic artifacts, commands, exit status and evidence are inserted
  by the server. Do not rewrite them or claim any generated test code was run.
  Static reproduction steps are hypotheses, not observed behavior. A nonzero
  exit code, compilation failure or sanitizer configuration alone does not prove
  a vulnerability. Non-crash findings can be supported by file/HTTP/network evidence.
- Do not include CVSS scores or severity ratings
- Do not include disclosure timelines
- Do not include references section
